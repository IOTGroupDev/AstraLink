## 1. Общее заключение

**AstraLink имеет основу полноценного продукта, но готовность к публичному и платному запуску по результатам аудитов не подтверждена.** Основные препятствия — границы доступа к персональным данным, достоверность состояния оплаты и работоспособность связки знакомства → переписка.

Реализованы React Native/Expo frontend, NestJS backend, Supabase Auth, Prisma, Redis и расчёты Swiss Ephemeris. Есть экраны натальной карты, гороскопов, совместимости, знакомств, чата, AI-советника, обучения и подписок. Проект можно исправлять последовательными изменениями в существующих модулях. Оснований переписывать приложение целиком аудит не установил.

Три аудита показывают взаимосвязанные проблемы:

| Направление               | Заключение                                                                                                                       | Практическое последствие                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Авторизация и доступ      | В живой БД общий AI-кэш и отчёты доступны всем authenticated; в исходниках отдельные public auth-маршруты не проверяют владельца | Требуется немедленно закрыть доступ и проверить все операции с service role      |

**Первый приоритет — закрыть P0; следующий — восстановить основные пользовательские сценарии и целостность данных.** Улучшение внешнего вида, широкую декомпозицию и новые возможности следует планировать после устранения блокеров.

Прямой доступ в Supabase подтверждён каталогами, grants и ролевыми проверками. Уязвимости backend подтверждены по локальным исходникам; совпадение размещённого backend с ними ещё нужно установить. Факт эксплуатации не установлен. Записи в аудите относятся к снимку 13 октября, а не к постоянным значениям.

## 3. Как читать сроки и роли

**Базовый ориентир — 10 недель, каждый спринт длится одну неделю с пятью рабочими днями.** Неделя 1 отсчитывается от фактического старта; календарные даты не назначены. Это оценка последовательности, а не гарантированный срок выпуска.

Предполагается один backend-разработчик на полной загрузке, один frontend-разработчик на полной загрузке, QA примерно на половину загрузки и доступная часть времени DevOps/ответственного за Supabase. Backend, платежи и изменения БД будут ограничивать параллельность. При одном разработчике или отсутствии staging план нужно пересчитать.

Первые восемь недель посвящены исправлениям, девятая — сквозной проверке и эксплуатации, десятая — регрессиям и кандидату релиза. При сложных миграциях или внешних ограничениях возможны дополнительные 1–2 недели. Проверка магазинами приложений в этот срок не включена.

Роли: **BE** — backend и SQL; **FE** — приложение; **QA** — независимая приёмка; **OPS** — окружения, развёртывание и восстановление; **PO** — продуктовые решения, тарифы и рекламные обещания. Фамилии назначаются при старте.

Каждую неделю первые четыре дня включают реализацию и проверки, последний — завершение приёмки и подготовку следующего спринта. Работу QA нужно начинать по мере появления изменений. За спринт принимается проверенный результат, а не число закрытых файлов.

## 4. Срочные действия до обычной очереди задач

В первый рабочий день подтвердить версию deployed backend, воспроизвести безопасные проверки доступа и подготовить минимальное закрытие P0. Известные открытые права не должны оставаться до позднего тематического спринта.

Проверить приоритетный порядок: public auth-маршруты → RLS/grants кэша и отчётов → mock → отмена действующих Stripe-подписок. Если полная реализация функции занимает больше недели, подготовить ограничение уязвимого пути. Для уже оплаченных пользователей нужен работающий механизм отмены, а не только отключение новых покупок.

Одновременно ограничить произвольные photo paths, записи служебных полей, незащищённые административные операции и обход блокировок. Ограничение риска относится к неделе 1; полное восстановление сценариев — к последующим спринтам. Проверки и минимально необходимый staging обеспечиваются сразу, без ожидания инфраструктурного спринта.

## 9. Спринт 4 — шифрование, Storage и удаление аккаунта

2. Убрать ограничение cleanup одной порцией 1000, обеспечить обход каталогов, повторяемость и контроль ссылок. Для 86 объектов исчезнувших пользователей и двух orphan AI-cache подготовить инвентаризацию и retention/grace period.
3. В production требовать ключ шифрования; проверить backfill трёх plaintext профилей. До очистки проверить реальное decrypt/GCM, сравнить значения и восстановление из backup.
4. Зафиксировать охват шифрования: users, compatibility partner data, birth context в natal JSON, координаты и логи. Не считать очистку users достаточной для всей БД.
5. Ограничить MIME/размер на уровне buckets и backend, привязать pending upload к пользователю; убрать общий ключ скрытия profile completion при завершении аккаунта.

**Основание:** F-05/F-08, T-09, DATA-01, CODE-05/06/07, S-STOR-02/03, prefix policies.

**Приёмка:** при недоступном Auth/Storage удаление возобновляется и не сообщает преждевременный успех. После завершения нет активной identity, данных/файлов за пределами согласованной retention и локальной session. Чужой namespace и неподдерживаемая загрузка отклоняются. Cleanup не стирает plaintext при неверном ключе или повреждённом ciphertext.

**Миграции:** возможны статус/job/outbox, upload lifecycle и ограничения путей. Массовое удаление объектов и plaintext выполняется отдельным проверенным этапом; нельзя удалять все unreferenced объекты только по одному запросу.

## 10. Спринт 5 — астрология, карты и AI-интерпретации

**Ответственные:** BE — расчёты; FE — отображение; QA — эталонные даты и периоды.

1. Явно выбрать средний или истинный северный узел; южный рассчитывать через 180°. Использовать константы Swiss Ephemeris и проверить аспектные результаты.
2. Сохранять вычисленную speed/ретроградность в Swiss API; закрепить UTC/offset контракт и исторические timezone для затронутых путей.
3. Ввести версию исправленного расчёта и план пересчёта сохранённых карт/отчётов/кэша. Не смешивать старые AI-тексты с обновлёнными позициями.
4. Проверить день/неделю/месяц, дату смены периода, язык, тариф, отказ AI и повтор запроса; истёкший кэш не считать актуальным.
5. Проверить лимиты советника, историю и понятное сообщение при отказе провайдера; интерпретации отделить от точных вычислений.

**Основание:** F-03/F-07, T-07, карта функций и проверки гороскопа/советника.

**Приёмка:** между выбранными узлами 180°; эталонные планеты/дома/аспекты проходят допуски, установленные командой по источнику расчёта. Один запрос даёт одинаковое UTC-значение в разных TZ процесса. Пересчёт возобновляется без дублей; пользователю показаны данные одной версии. AI-ошибка не заменяет расчёты вымышленными позициями.

**Влияние на данные:** результаты южного узла, его аспектов и интерпретаций изменятся; пересчёт и инвалидирование кэша требуют наблюдения и оценки стоимости AI. Проверка полноты ephe для поддерживаемых дат обязательна.

## 11. Спринт 6 — знакомства, RPC и ранжирование

**Ответственные:** BE — RPC/выборка; FE — лайки/пустые состояния; QA — два и более тестовых профиля; PO — правила поиска.

1. Исправить create_like UUID/text и бизнес-проверки; дать точечный EXECUTE после проверки тела, а не просто открыть существующую функцию.
2. Проверить like/pass/super_like, повтор действия, взаимный match, фильтры и отсутствие кандидатов. Ошибочный ответ не должен выглядеть сохранённым действием.
3. Общие проверки блокировки/видимости/готовности профиля должны работать и через backend, и через доступные direct RPC; учитывать expires_at кэша кандидатов.
4. Реализовать реальное плановое ранжирование на согласованных расчётах, с лимитами и наблюдением результата. Ограничить rank/run администратором/внутренним запуском и защитить от параллельных jobs.
5. Проверить согласованность public_profiles/primary photo и устранить два расхождения onboarding с единым источником состояния, сохранив возможность восстановления незавершённого профиля.

**Основание:** S-RPC-01/02/04, CODE-04, onboarding mismatch, матрица dating функций.

**Приёмка:** симпатия сохраняется, ответная создаёт одну пару, запреты не обходятся прямым RPC. Nightly job проверяется по актуальному содержимому и версии scores, а не только status succeeded; расчёты не подменяются заглушкой. Неполные/заблокированные профили исключаются по согласованным правилам.

**Риски:** настоящий ranking может потребовать больше недели. В таком случае его выделяют в отдельный спринт; выпуск без него возможен только при рабочем проверенном подборе и исключении обещания ночного ранжирования из состава релиза.

## 12. Спринт 7 — сообщения, Realtime и история

**Ответственные:** BE — выборка/запись; FE — история/reconnect; QA — два устройства и разные роли.

1. Фильтровать участников диалога и сортировать до LIMIT; добавить cursor по времени/ID, загрузку старых страниц и отдельное состояние ошибки API.
2. Закрепить одну схему колонок и контракт отправки; исправить или закрыть неиспользуемые send_message overloads. Сократить fallback, вызывающий повторные undefined-column ошибки.
3. Проверять match status/block и media ownership на всех допустимых путях; запретить клиентскую подстановку system/read_at/служебных дат там, где это серверные значения.
4. Заменить interface DTO на валидируемые классы, проверить UUID/limit/размер текста, унифицировать Bearer parsing.
5. После проверки RLS/блокировок включить public.messages в publication. Обработать reconnect, дубли событий, read receipts, медиа и удаление у себя/для всех.

**Основание:** F-04, T-08/T-11, RT-01/CHAT-01, S-RPC-03, messages INSERT, OPS-01.

**Приёмка:** последние сообщения каждого диалога отображаются при нескольких переписках; история свыше 100 сообщений читается без пропусков/дублей. Входящие приходят на второе устройство без повторного открытия экрана. Заблокированная/запрещённая отправка не проходит API или direct write. Отказ БД не выглядит пустой перепиской; удаление чужого сообщения для всех невозможно.

**Миграции:** RPC/grants/publication и при необходимости индексы пагинации; публикация не расширяет доступ к чужим строкам. Presence privacy и невозможность подменять собственность событий проверяются отдельно.

## 13. Спринт 8 — мобильный путь, onboarding и готовность функций

**Ответственные:** FE; BE поддерживает API; QA — iOS/Android; PO подтверждает состав релиза.

3. Paywall открывается по подтверждённому состоянию тарифа, не по finally ошибочного refetch; trial/отмена/возврат из оплаты не создают лишнюю навигацию.

**Основание:** функциональная карта, риски OAuth/paywall, CODE-02B, F-08, T-12 и рекламное описание.

**Приёмка:** все основные маршруты проходят на физических iOS/Android устройствах; удалённый/предыдущий пользователь не оставляет session или настройки нового. ## 17. Общая готовность задачи и релиза

Каждая задача имеет ссылку на находку, ответственного, проверку до/после и свидетельство приёмки: результат CI, тестовый сценарий, безопасный SQL-агрегат или проверку провайдера. Для изменения БД дополнительно нужны миграция, анализ существующих данных, стратегия применения и восстановление. Итоговая версия приложения остаётся совместимой с согласованными API и сессиями.

К публичному выпуску закрыты известные P0, закрытые данные других пользователей недоступны, подтверждены основные Auth/onboarding/chart/dating/chat/delete сценарии. К платному выпуску дополнительно подтверждены реальные покупка/trial/отмена/истечение доступа, обработка повторов и история операций. Для обеих стадий выполнены обязательные проверки CI и мобильная приёмка.

Функция может быть отложена только при явном исключении из релиза и интерфейса/рекламных обещаний. Нельзя считать блокер закрытым только потому, что пользователь не видит кнопку, когда опасный API/RPC остаётся доступен. Незакрытые P0/P1 основных сценариев переносят выпуск; P2 сопровождаются планом и приоритетом.

## 18. Команды проверки

Команды запускаются из корня проекта. Локальные проверки:

```bash
(cd backend && npm run build)
(cd backend && ./node_modules/.bin/eslint '{src,apps,libs,test}/**/*.ts')
(cd backend && npm test -- --runInBand)
(cd frontend && npx tsc --noEmit)
(cd frontend && npm test -- --runInBand)
```

Для подготовленного тестового окружения:

```bash
(cd backend && npx prisma generate)
docker compose up --build
(cd frontend && eas build --platform ios --profile preview)
```

`npm run lint` backend включает --fix; для контроля без изменения файлов выше указан прямой ESLint. Root frontend:build/frontend:lint не считать рабочими, пока в frontend не определены соответствующие scripts.

`npx prisma migrate dev` применяется только к development БД, `npx prisma migrate deploy` — после просмотра SQL и подготовки выбранного окружения. Docker startup уже вызывает deploy; compose-проверка должна использовать тестовый URL. План не запускает эти команды и не применяет миграции.

## 19. Финальное заключение для управления проектом

Приоритетный путь AstraLink — **закрыть доступ → стабилизировать оплату → обеспечить воспроизводимую схему и удаление → исправить расчёты → восстановить знакомства и чат → подтвердить мобильные сценарии и эксплуатацию**.

Проект имеет работающие строительные блоки и достаточный функциональный объём для последовательного доведения до релиза. Основная работа сейчас заключается в согласовании прав, данных и поведения функций между frontend, backend и живым Supabase. Расширение продукта до завершения этой цепочки увеличит объём повторных исправлений.

План на десять недель даёт проверяемые результаты каждой недели и место для интеграции. Решение о выпуске принимается по выполненным критериям, подтверждённой версии и составу функций. Этот файл содержит заключение и базовый план. Выполненные изменения, результаты проверок и ограничения учитываются отдельно в [прогрессе первого спринта](SPRINT_1_PROGRESS_2026-10-13.md).
