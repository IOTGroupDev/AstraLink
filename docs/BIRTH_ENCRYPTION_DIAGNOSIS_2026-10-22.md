# AstraLink — диагностика ошибки расшифровки birth fields

Дата: 22 октября 2026 года. **Старые данные пока не восстановлены.** Проверен ключ из существующего `backend/.env`, подготовлены совместимое чтение прежними ключами и команда проверки без записи в БД. Другой подтверждённый ключ не найден; действующий `.env` не изменялся.

## Значение предупреждения

`Unsupported state or unable to authenticate data` возникает при проверке AES-GCM: используемый ключ, ciphertext и authentication tag не согласованы. Причиной может быть другой ключ или повреждение записи. Успешный разбор строки `v1.iv.ciphertext.tag` не доказывает корректность её расшифровки. [Документация Node.js](https://nodejs.org/download/release/v24.18.0/docs/api/crypto.html#deciphersetauthtagbuffer-encoding).

Сервис возвращает legacy plaintext fallback, если он существует, либо null. Это влияет на доступность данных рождения для профиля и расчётов; проблема отличается от истечения JWT и сохранения сессии в Keychain.

## Проверено на live Supabase без записи

Проверка использовала текущий ключ из `backend/.env` только в локальном процессе. Из БД запрашивались encrypted fields; ключ, ciphertext и расшифрованные значения не выводились. Дополнительный SQL вернул только агрегаты наличия plaintext.

Последний снимок проверки:

| Источник                           | Всего записей | Записей с encrypted data | Записей с ошибкой | Читаемых полей | Нечитаемых полей |
| ---------------------------------- | ------------- | ------------------------ | ----------------- | -------------- | ---------------- |
| users                              | 16            | 7                        | 6                 | 3              | 18               |
| compatibility_reports partner data | 6             | 6                        | 1                 | 15             | 3                |

В начале проверки не читалось ни одно из 21 encrypted fields пользователей. Во время работы одна encrypted user record обновилась в БД; последующий снимок читает три поля. Диагностика не выполняла эту запись. Файл `.env` между проверками не менялся. Все семь encrypted user records при проверке наличия plaintext были без plaintext birth fallback.

Формат, IV и tag длины у исходно проверенных записей корректны. Текущий ключ подходит к части данных, что указывает на использование разных ключей. Повреждение оставшихся записей окончательно не исключено. Наличие ключа в `backend/.env` не подтверждает, что им зашифрованы все исторические записи; повторное добавление того же значения не поможет.

## Подготовлено в коде

- [SensitiveProfileEncryptionService](../backend/src/common/services/sensitive-profile-encryption.service.ts) пробует действующий ключ и до восьми прежних ключей при чтении. Новые записи всегда шифруются `DATA_ENCRYPTION_KEY`; формат v1 сохранён. Ошибка логируется, только если ни один ключ не прошёл authentication. Некорректный список ключей отклоняется без вывода секретов.
- Новая необязательная переменная `DATA_ENCRYPTION_PREVIOUS_KEYS` — JSON-массив строк. Она добавлена в конфигурацию, examples и Compose. Значения в действующие окружения не добавлялись.
- [Read-only audit](../backend/src/scripts/audit-birth-encryption.ts) проверяет users и compatibility_reports и печатает только счётчики. Exit 0 — все имеющиеся encrypted fields прочитаны, exit 2 — есть нечитаемые поля, exit 1 — ошибка настройки/запроса.
- Проверены **430/430 backend-тестов**, сборка, lint без ошибок (четыре прежних предупреждения вне изменений) и разбор Compose. Тесты включают чтение старого и текущего ключей, запись только текущим ключом, отказ при неверных ключах/повреждённом ciphertext и сохранение legacy fallback.

## Что требуется для восстановления

1. Найти **другой подтверждённый ключ**, например в прежней конфигурации Dokploy или более раннем `.env`. Сам секрет не отправлять в чат. Доступный сейчас `backend/.env` уже проверен и сам по себе проблему не устраняет.
2. Сохранить текущий `DATA_ENCRYPTION_KEY`. Добавить другой ключ в `DATA_ENCRYPTION_PREVIOUS_KEYS` в том окружении, которое читает БД. Формат ниже содержит placeholder, а не рабочий секрет:

   ```dotenv
   DATA_ENCRYPTION_PREVIOUS_KEYS='["<другой_прежний_ключ>"]'
   ```

3. Проверить только чтение с этим списком:

   ```bash
   cd backend
   npm run audit:birth-encryption
   ```

4. После успешной проверки развернуть изменённый backend с тем же списком ключей и перезапустить процесс. Изменение `.env` не обновляет ключи уже созданного экземпляра сервиса.
5. Проверить профили и расчёты. Перешифрование/ротацию и удаление plaintext выполнять отдельной согласованной операцией после backup и проверки чтения. Этот фикс сам не переписывает данные и не запускает backfill/cleanup.

Если другой подходящий ключ не сохранён, штатно восстановить данные можно из достоверной резервной копии или повторного ввода. Замена действующего ключа случайным новым не расшифрует старые записи.
