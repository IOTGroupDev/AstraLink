# Функциональный аудит AstraLink

Дата: 13 октября 2026 года. База: commit `1fd19ff` и текущее рабочее дерево, включая незакоммиченные изменения.

## Вывод

В приложении реализованы основные направления: авторизация, onboarding, гороскоп, натальная карта, знакомства, переписка, AI-советник и подписки. Однако готовность к платному запуску не подтверждена: найдены ошибки отмены подписки, возможность активации платного доступа без оплаты, неверный расчёт южного лунного узла и неполная выборка сообщений.

Это аудит реализации и локальных автоматических проверок. Приложение не запускалось на физическом устройстве; реальные Supabase, Stripe, push, magic link и production API не проверялись. Наличие экрана или endpoint не означает успешность полного пользовательского сценария. Старые аудиты из `docs` не использовались как доказательство текущих дефектов.

Приоритеты: **P0** — блокирует платный запуск; **P1** — существенно нарушает основной сценарий; **P2** — ухудшает опыт или требует уточнения. «Подтверждено по коду» означает конкретную ветку реализации; риски внешних интеграций требуют проверки в staging.

## Подтверждённые проблемы

### F-01 · P0 · Отмена подписки не прекращает автопродление в Stripe

**Доказательство:** `backend/src/subscription/subscription.service.ts`, `cancel()` (строка 993): изменяет только `isCancelled` в PostgreSQL и очищает Redis. Обращения к Stripe нет. `frontend/src/services/api/subscription.api.ts` вызывает этот endpoint. Ответ обещает, что подписка отменена.

**Последствие:** для активной Stripe-подписки пользователь получает подтверждение отмены, а провайдер продолжает автопродление. Последующий webhook может вернуть локальный флаг к состоянию провайдера.

**Рекомендация:** отменять продление конкретной Stripe-подписки через провайдера; после подтверждения синхронизировать локальное состояние. Учесть несколько подписок, retries и ошибки Stripe.

**Приёмка:** после отмены Stripe показывает `cancel_at_period_end=true`, доступ сохранён до конца периода, повторная отмена безопасна, следующий период не оплачивается.

### F-02 · P0 · Платный доступ можно получить mock-запросом

**Доказательство:** `backend/src/subscription/subscription.controller.ts`, `upgrade()`; `subscription.service.ts`, `upgrade()` (363), `processMockPayment()` (720), `processPaidPayment()`. Mock принимается без ограничения `NODE_ENV`; он записывает платный tier и месячный срок. Авторизация есть, проверка реальной оплаты в этой ветке отсутствует.

**Последствие:** авторизованный пользователь может активировать premium/max без покупки. Для воспроизведения в изолированном тестовом окружении достаточно `POST /api/v1/subscription/upgrade` с `{"tier":"premium","paymentMethod":"mock"}` и валидной session. Не проверять на реальном платном аккаунте.

**Рекомендация:** закрыть mock в production на сервере; доступ выдавать только после проверенного события провайдера.

**Приёмка:** mock и неподдерживаемый способ оплаты не меняют тариф в production; подтверждённая покупка изменяет его ровно один раз.

### F-03 · P1 · Под южным узлом возвращается истинный северный узел

**Доказательство:** `backend/src/services/ephemeris.service.ts`, таблица `planetNames`: 10 → `north_node`, 11 → `south_node`. В установленной библиотеке `swisseph/lib/swisseph.js` 10 — `SE_MEAN_NODE`, 11 — `SE_TRUE_NODE`. Это средний и истинный северные узлы.

Локальный вызов Swiss Ephemeris с файлами `backend/ephe` для 1990-01-01 12:00 UTC дал 318.4349837° для 10 и 316.8702736° для 11: значения близки, а южный узел должен быть противоположен выбранному северному на 180°.

**Последствие:** неверны положение южного узла, его знак, аспекты и интерпретации, использующие эти данные. Это ошибка соответствия объектов, а не имитация расчётов: библиотека действительно вызывается.

**Рекомендация:** выбрать средний или истинный северный узел и рассчитывать южный как `(north + 180) % 360`; пересчитать затронутые сохранённые карты и AI-кэш по отдельному плану.

**Приёмка:** расстояние между узлами 180° на наборе дат; аспекты и тексты используют пересчитанные значения.

### F-04 · P1 · История диалога может быть неполной даже в пределах последних 100 сообщений

**Доказательство:** `backend/src/chat/chat.service.ts`, `listDialogMessages()` (490): сначала выбирает ограниченную порцию всех доступных RLS сообщений через `select('*').limit(...)` без фильтра собеседника и сортировки, затем фильтрует диалог в памяти. `frontend/src/screens/ChatDialogScreen.tsx:393` запрашивает 100 сообщений; `frontend/src/services/api/chat.api.ts` не передаёт cursor/offset для истории.

**Последствие:** сообщения других диалогов расходуют лимит; нужный диалог может выглядеть пустым или потерять свежие сообщения. История более 100 сообщений не имеет реализованного API для постраничного чтения.

**Рекомендация:** фильтровать участников и сортировать на сервере до LIMIT; добавить cursor-пагинацию по дате и ID.

**Приёмка:** при нескольких переписках отображаются последние сообщения выбранного диалога, старые страницы загружаются без пропусков и дублей.

### F-05 · P1 · Удаление может завершиться успехом при сохранённом Supabase Auth аккаунте

**Доказательство:** `backend/src/user/user.service.ts`, `deleteAccount()` (733): после DB-транзакции очищает Storage и Auth. Ошибки Storage и ошибка `deleteUser` записываются в журнал, но не мешают успешному завершению. `frontend/src/screens/ProfileScreen.tsx` после API выполняет локальную очистку.

**Последствие:** основная DB-информация удалена, но внешняя identity или файлы могут сохраниться. Возможность восстановления профиля при следующем входе зависит от auth-потока и должна быть проверена отдельно.

**Рекомендация:** хранить статус незавершённого удаления, повторять внешнюю очистку и давать пользователю корректный статус; не сообщать о полном завершении до выполнения всех стадий.

**Приёмка:** искусственный отказ Auth/Storage приводит к контролируемому повтору, итоговая проверка подтверждает отсутствие identity, файлов и локальных данных.

### F-06 · P1 · Повтор подтверждения Stripe создаёт новую подписку

**Доказательство:** `subscription.service.ts`, `confirmStripePayment()` (431): проверяет владельца и статус SetupIntent, затем каждый раз вызывает `stripe.subscriptions.create`. Нет idempotency key или проверки уже обработанного SetupIntent; каждый вызов задаёт trial. При создании PaymentSheet также каждый раз создаётся новый customer.

**Последствие:** двойное нажатие или сетевой повтор могут создать несколько подписок и будущих списаний; повторный trial не ограничен в этой ветке данными прежнего trial.

**Рекомендация:** сделать подтверждение идемпотентным и повторно использовать customer; проверять право на trial на сервере.

**Приёмка:** последовательные и параллельные подтверждения одного SetupIntent дают одну подписку; использованный trial повторно не выдаётся.

### F-07 · P2 · Скорость планет в Swiss API всегда нулевая

**Доказательство:** `backend/src/modules/swiss/swiss.service.ts`, `calculatePlanetPositions()`: устанавливает `speed: 0`, хотя `EphemerisService.calculatePlanets()` возвращает скорость и `isRetrograde`.

**Последствие:** потребители `/swiss/planets` не могут корректно определять ретроградность. Распространение на основной натальный экран не установлено: основной расчёт использует другой путь.

**Приёмка:** API сохраняет вычисленную скорость; заведомо ретроградная планета имеет отрицательное значение.

### F-08 · P2 · Настройка скрытия предложения заполнить профиль переживает удаление

**Доказательство:** `frontend/src/navigation/TabNavigator.tsx` использует общий ключ `profile_completion_hide_popup`; `frontend/src/services/cleanupService.ts` не удаляет этот ключ ни по имени, ни по префиксу.

**Последствие:** новый пользователь на том же устройстве может не получить предложение заполнить профиль, если предыдущий его скрыл.

**Приёмка:** настройка привязана к пользователю либо очищается при завершении его жизненного цикла.

## Риски, требующие сценарной проверки

- `MainStackNavigator.tsx` автоматически открывает paywall после `refetch().finally()`. Проверить поведение при недоступном API: решение о показе не должно опираться на ошибочный статус.
- `oauthSessionRouting.ts` при session без переданного профиля устанавливает `onboardingCompleted=false`. Проверить, что существующий заполненный пользователь после OAuth не проходит onboarding повторно.
- Блокировки кандидатов реализованы в dating service, но запрет отправки сообщений требует проверки действующих RPC/RLS в Supabase. Отсутствие проверки в TypeScript само по себе не доказывает обход.
- В upgrade Apple/Google отклоняются как неподдерживаемые. Требования к каналам покупки и восстановлению покупок нужно определить отдельно; соответствие правилам магазинов в этом аудите не оценивалось.

## Проверки и порядок работ

Фактически выполнены: backend build — успешно; frontend TypeScript — успешно; frontend Jest — 10/10 наборов и 75/75 тестов; backend Jest — 8/13 наборов прошли, 5 упали, 110 тестов прошли и 3 упали среди запущенных. Наборы, не прошедшие компиляцию, в число выполненных тестов не входят.

1. До платного запуска закрыть F-01/F-02, затем F-06.
2. Исправить F-03 с контролируемым пересчётом, F-04 и F-05.
3. Пройти staging-сценарии: регистрация → onboarding → карта → знакомства → взаимный лайк → текст/медиа → блок → удаление.
4. Проверить платный цикл: trial → успешная/неуспешная оплата → повтор webhook → отмена → окончание доступа.
5. Повторить сценарии на iOS/Android с перезапуском, медленной сетью и сменой пользователя.

Команды локальных проверок:

```bash
(cd backend && npm run build)
(cd backend && npm test -- --runInBand)
(cd frontend && npx tsc --noEmit)
(cd frontend && npm test -- --runInBand)
```

Аудит не меняет приложение или схему БД. Пересчёт карт, изменения хранения платежей и механизма удаления потребуют отдельных изменений и плана обработки существующих данных. Технические причины и инфраструктурные ограничения: [технический аудит](TECHNICAL_AUDIT_2026-10-13.md).
